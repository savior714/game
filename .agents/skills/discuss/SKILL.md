# Discuss skill

workflow 진입점은 [`discuss.md`](../../workflows/discuss.md)다.

## 1. 시작 전 조사

질문 전에 현재 저장소에서 확인 가능한 맥락을 읽는다.

- `AGENTS.md`
- `PROJECT_RULES.md`
- 가장 가까운 product spec
- 직접 관련 code/test/config
- 이미 사용자가 확정한 선택

질문으로 파일·경로·현재 기능 상태를 대신 조사하지 않는다.

## 2. 결정축 설계

좋은 결정축은 하나의 문장으로 설명할 수 있다.

예:

- 안정화 종료 조건
- 첫 대상 선정 방법
- 완료 증명 수준
- 공용화 시점
- UI/UX 포함 범위
- 게시 단위

나쁜 질문은 서로 다른 축을 한 선택지에 섞는다.
예를 들어 “모든 과목을 강한 브라우저 테스트로 한 번에 리팩터링한다”는 범위, 증명 수준, 구현 방식이 혼합돼 있으므로 분리한다.

## 3. 선택지 품질

선택지는 2~4개로 제한하고 다음을 확인한다.

- 동일한 결정축인가
- 서로 동시에 참일 수 없는가
- 차이가 실제 결과를 바꾸는가
- 권장안은 정확히 하나인가
- 권장 표시와 결론이 같은가
- 사용자가 선택 후 무엇이 고정되는가

선택지 하나를 사실상 정답으로 만들기 위해 다른 선택지를 비현실적으로 약하게 쓰지 않는다.

## 4. 권장안

권장안은 다음 순서로 고른다.

1. 사용자가 이미 밝힌 목적과 제약
2. 현재 제품 계약
3. 안전성·복구 가능성·검증 가능성
4. 개발 속도와 유지보수 비용

근거가 부족하거나 사용자의 가치 판단만으로 결정되는 경우 권장 표시를 생략할 수 있다.

## 5. 설명 수준

사용자가 이해하기 어려워하면 결정 결과가 실제 개발에서 무엇을 바꾸는지 쉬운 예로 설명한다.

- 어떤 작업이 먼저 오는가
- 무엇은 당분간 하지 않는가
- 언제 완료로 판단하는가
- 다음 결정은 무엇인가

기술 용어가 필요한 경우 간단한 의미를 함께 적는다.

## 6. edge case

모든 논의에서 예외 질문을 형식적으로 삽입하지 않는다.
선택한 방향이 다음 상황에서 달라질 가능성이 있을 때만 별도 결정축으로 다룬다.

- 빈 데이터
- 저장 실패
- offline 또는 network failure
- 권한 부족
- 중복 입력
- 마지막 항목과 restart

현재 결정에 영향을 주지 않는 edge case를 질문 수를 늘리기 위해 추가하지 않는다.

## 7. 문서화

사용자가 문서 반영을 요청하면:

1. 현재 authority 문서를 찾는다.
2. 결정의 역할에 맞는 문서만 갱신한다.
3. README·AGENTS·MEMORY 전파가 필요한지 판단한다.
4. 링크와 policy guard를 검증한다.
5. 일정 진행률이나 선택 과정 전체를 저장하지 않는다.

별도 discussion note와 plan은 명시적 요청이 있을 때만 만든다.

## 8. 종료

논의가 끝나면 확정된 결정만 정리한다.
다음 작업을 자동 plan으로 전환하거나 선택 질문을 강제로 붙이지 않는다.
사용자가 구현을 요청하면 현재 결정에 맞는 첫 실행 경계를 선택한다.

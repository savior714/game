# Discuss workflow

상세 절차는 [`discuss/SKILL.md`](../skills/discuss/SKILL.md)를 따른다.

## 1. 사용 조건

- 제품 방향이나 우선순위가 아직 확정되지 않음
- 여러 구현 선택지 중 사용자 결정이 필요함
- 수용 기준·포함 범위·동결 범위를 좁혀야 함
- 코드 변경 없이 현재 상태와 trade-off를 논의해야 함

이미 objective와 criterion이 명확한 구현 요청에는 discuss를 삽입하지 않는다.

## 2. 기본 경계

- discuss 중 production code를 수정하지 않는다.
- 일반 대화는 채팅에서 관리한다.
- 사용자가 저장소 논의 노트나 Blueprint를 명시적으로 요청하지 않았다면 파일을 만들지 않는다.
- 과거 plan·backlog를 현재 방향의 권위로 사용하지 않는다.
- 저장소에서 확인 가능한 사실은 먼저 조사하고 사용자에게 되묻지 않는다.

## 3. 한 질문 = 한 결정축

사용자 결정이 필요한 경우:

1. 질문 하나에는 정확히 하나의 결정축만 둔다.
2. 선택지는 같은 축에 있고 상호 배타적이어야 한다.
3. 권장 기본값은 정확히 하나만 표시한다.
4. 표시된 권장안과 본문 결론이 일치해야 한다.
5. 선택으로 무엇이 확정되고 무엇이 남는지 설명한다.

제품 수용 기준, 증명 강도, 테스트 아키텍처, 구현 분해, 운영 방식을 한 질문에 섞지 않는다.
두 선택지가 동시에 참일 수 있으면 질문을 분리한다.

## 4. 질문이 필요하지 않은 경우

- 최신 저장소 증거로 답을 결정할 수 있음
- 이미 사용자가 같은 결정을 내렸음
- 경미한 세부사항이며 가정이 결과를 바꾸지 않음
- 사용자가 직접 구현·수정·검증을 요청함

이 경우 질문 도구나 선택 메뉴를 형식적으로 호출하지 않고 작업 또는 설명을 계속한다.

## 5. 현재 AidenGame 기본 방향

현재 확정된 방향은 `docs/specs/product/CORE_QUIZ_RELIABILITY_STABILIZATION.md`에 있다.

- 일반 과목 문제풀이 신뢰성 우선
- 네 과목 모두 안정화 후 신규 기능 재개
- Ocean Rescue와 실험 기능 구조 이전 동결
- 상태 계약과 실제 브라우저 증거 병행
- 첫 과목은 공통 진단 결과로 선택
- 두 번째 과목에서 반복이 확인된 뒤에만 공용화 검토
- 오조작을 유발하는 UI/UX 포함, 순수 시각 개선 제외
- 과목 단위 게시

이미 확정된 축을 다시 질문하지 않는다.
새로운 방향 변경 요청이 있을 때만 해당 결정축을 논의한다.

## 6. 결과 정리

논의가 수렴하면 채팅에서 다음을 정리한다.

- 확정된 결정
- 결정이 적용되는 범위
- 명시적 non-goal
- 아직 미결정인 다음 결정축이 있다면 하나

저장소 문서 반영을 사용자가 요청했다면 authority에 맞는 기존 문서를 갱신한다.
단순 진행 기록용 `DISCUSS_*.md`를 자동 생성하지 않는다.

## 7. 종료

- 필수 handoff menu를 호출하지 않는다.
- 자동으로 Blueprint를 만들지 않는다.
- 사용자가 더 이상 논의를 원하지 않으면 확정 사항을 요약하고 종료한다.
- 구현까지 요청받았다면 최신 main에서 첫 단일 failure domain으로 전환한다.
